# DeskBurn 踩坑记录

这份文档保留从黑屏排障、UI 渲染、CC Switch 聚合、BLE 通信到固件部署过程中
最值得复用的经验。这里记录的是当前代码依赖的约束，不只是历史故事；修改相关
代码前请先确认对应测试和硬件假设仍然成立。

## 屏幕与 SPI

### SCLK 接错时，串口和背光仍然正常

最初使用 GPIO10 作为时钟，设备表现为：

- 背光正常；
- `setup()` 正常运行；
- 串口心跳正常；
- `display.init()` 不报错；
- 屏幕始终全黑。

根因是 AirM2M CORE ESP32-C3 的默认 SPI 为 `SCK=GPIO2`、`MOSI=GPIO3`、
`MISO=GPIO10`。GPIO10 是 MISO，不是时钟。屏幕初始化通常不会回报 SPI 从机
是否响应，因此“程序正常”不能证明显示总线正常。

### 3.5 寸不等于 480×320

物理尺寸不能推导分辨率。本机外观看起来像常见的 480×320 面板，实测却是
240×320，横屏为 320×240。换屏时应画满屏边框和测试色块，不要只看中央文字。

### 没有 LCD MISO 时，读不到控制器 ID

对命令 `0xD3` 的回读始终为 `0x000000`，因为转接板没有引出 LCD MISO。
这不是控制器不存在，也不是读命令一定错误。此时只能用候选初始化序列逐组试画。

仓库中的 `pin_scanner` 把引脚和初始化序列放到运行时选择，一次烧录即可轮换
多组假设，避免每试一组都重新编译和烧录。

### 灰阶画面无法验证 RGB/BGR 色序

背景、白字和灰色分隔线的 R/B 分量接近或相同，即使色序配置错误，肉眼也可能
看不出来。直到显示 Claude 的橙色标识时，红蓝交换才暴露。

验证新面板时必须显示至少一种 R/B 明显不对称的颜色。当前面板配置为：

```ini
-D TFT_RGB_ORDER=TFT_BGR
```

## 位图与局部刷新

### TFT_eSPI 2.5.0 的三参数 `alphaBlend` 链接失败

症状：

```text
undefined reference to `TFT_eSPI::alphaBlend(unsigned char, unsigned short, unsigned short)'
```

该版本在头文件中声明了 inline 函数，却没有向外提供可链接的实现。正式固件
自带 `blendRgb565()`，不要为了“使用库函数”删掉它。

### `pushImage` 要处理 RGB565 字节序

ESP32 是小端，面板传输要求 RGB565 高字节在前。`pushImage` 直接发送缓冲区
内存，不调用 `setSwapBytes(true)` 时会出现：

- 白色 ASCII 文字正常，因为 `0xFFFF` 交换后不变；
- 位图颜色错误；
- 图标周围出现与背景不一致的色块。

正式固件只在推送 alpha 位图期间开启字节交换，结束后恢复，避免影响 TFT_eSPI
其他绘图路径。

### 局部刷新不能整行擦除

金额变化时曾按屏幕全宽擦除所在水平带，结果把同一高度的图标和标签一起清掉。
而且问题只在第一次动态刷新后出现，静态布局看起来完全正确。

当前实现记录上一次内容的真实包围盒，只擦旧包围盒再绘制新内容。新增动态组件
时也应遵循这个规则，不要把“局部刷新”写成“整行清屏”。

### 240 高排四行文字后必须按擦除带留间距

三栏金额下面各挂一行 Token 数之后，纵向已经接近排满。周期金额使用 Font4，
底部 Token 使用 22px SF Pro Bold 离线字形（实际笔画高 16px），两行分别按
自己的真实包围盒局部擦除。

改 `Layout` 里任何一个 Y 坐标前，按各元素的真实高度重算一遍：图标 34px、
中文标签 23px、金额字形 38px（擦除带 46px）、Font4 26px、周期 Token 字形
16px。当前周期金额和 Token 的擦除带分别占 185..215 与 216..236；两块擦除带
一旦交叠，刷新时就会互相啃掉像素，而首屏静态布局看起来完全正常——和整行清屏
那个坑是同一类症状。

### `.ino` 会被自动合并

PlatformIO 会合并同一 `src_dir` 下的 `.ino` 文件。两个固件都定义
`setup()`/`loop()` 时会发生重复定义。项目统一使用 `.cpp`，并通过不同 env 的
`build_src_filter` 隔离正式固件和扫描固件。

### 中文与 SVG 需要离线光栅化

TFT_eSPI 内置字体主要覆盖 ASCII，MCU 也不能直接渲染 SVG。项目在 Mac 上把
中文、金额字形和 SVG 转成 8 位 alpha 蒙版，编译进 `assets.h`，运行时再上色。

3.5 寸 320×240 面板像素密度低，中文抗锯齿容易发灰。生成脚本使用 gamma
曲线增强中间 alpha，使笔画更实。普通固件构建直接使用仓库中的 `assets.h`，
不需要重新生成资源。

## CC Switch 数据口径

### SQLite 连接必须是真只读

采集端使用：

```python
sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)
```

这比代码约定“不执行写语句”更可靠，SQLite 自身会拒绝该连接上的写操作。

### CC Switch 写库时要等待

数据库可能使用 DELETE journal 而不是 WAL。CC Switch 持有写锁时，短暂读失败
是正常情况。采集端设置 `busy_timeout`，长跑服务遇到一次失败只跳过当前轮次，
保留设备上的旧数据，不清零也不重启。

### Token 口径按 `app_type` 区分

当前经过成本反算验证的规则：

```text
codex   = input + output
claude  = input + output + cache_read + cache_creation
```

Codex 的 `input_tokens` 已包含缓存部分；Claude 的四项互斥。数据库中的
`input_token_semantics` 在已验证数据上不能可靠表达这条差异。

### 必须跨 `data_source` 去重

同一次请求可能同时出现在代理日志和会话导入日志中。当前使用
`(app_type, 四个 token 字段, created_at)` 作为指纹，优先保留字段更完整的
`proxy` 记录。

不能从指纹中删除 `created_at`：不同时刻完全可能产生相同 Token 数，删除时间
会把正常请求误判成重复。

### 总计来自日志层和归档层

`proxy_request_logs` 覆盖近期明细，`usage_daily_rollups` 保存更早的按日归档。
总计要合并两层，并按仍在明细中的日期排除归档重叠。归档只有聚合结果，无法重新
执行跨来源去重，因此总计可能存在很小的历史偏差；今日、本周和本月不受影响。

### 本周一不能直接写 `weekday 1, -7 days`

SQLite 的 `weekday 1` 在周一当天会返回当天，再减 7 天就错到上周。当前代码按
星期序号计算回退天数，这个逻辑只在周一容易暴露问题，修改日期 SQL 时务必保留
周一测试。

## BLE 协议与运行

### v3 是固定 42 字节，不是旧版 30 / 26 字节

Python 与 C++ 各实现一次线格式：

```text
tools/ccswitch_agent/protocol.py
firmware/deskburn/link_protocol.h
```

字段顺序、端序、packed 布局、CRC 和版本必须同时修改。更新结构后必须：

1. 同步修改两端；
2. 升协议版本；
3. 运行全部协议测试；
4. 同一维护窗口内烧录固件并重启 Mac agent。

只升级一端时，设备会因版本不匹配拒绝整包并显示 `OFFLINE`。这是安全退化，
比错位读取字段更容易发现。

### Token 按「千 token」传输，不传原始计数

包里所有 Token 字段都是 u32，装的是千 token；金额同理是千分之一美元。

原始计数装不下总计：实测总计已到 18 亿，并以每月约 15 亿的速度增长，u32 的
42.9 亿撑不到年底。溢出后被夹住的表现是屏幕永远停在 `4.29B` —— 一个看着合理
却不再变化的数，比断连更难发现。

也没有改成 u64：设备端 `State` 里的字段是 `volatile uint32_t`，靠「32 位读写在
C3 上是原子的」省掉了锁；换成 64 位后，BLE 回调写到一半被主循环读走，会渲染出
高低半字来自不同包的乱数。屏幕最细只显示到 `0.01M`（即 10K），千位精度足够，
所以降精度比加宽度划算。

对账时 CLI 打的是原始 Token 数，屏幕上是取整过的，两者有个千位以内的差异是
预期的。

### 设备发现使用广播名，不使用地址

macOS 会为 BLE 外设暴露本机生成的标识，换电脑或重装系统后可能变化。Agent
按广播名 `DeskBurn` 查找设备，不写死地址。

### macOS 蓝牙权限绑定解释器路径

蓝牙授权可能绑定 Python 可执行文件的绝对路径。更换虚拟环境或升级解释器后，
可能出现“没有报错但一直扫不到设备”。遇到这种情况应：

1. 确认 launchd plist 使用的是当前虚拟环境 Python；
2. 在前台运行一次 `--serve --fake`，触发系统授权；
3. 检查“系统设置 → 隐私与安全性 → 蓝牙”；
4. 重新安装 launchd 服务。

`tools/install_launchd.py` 会把当前 `sys.executable` 写入 plist，避免模板写死
维护者的路径。

### NVS 不能每 30 秒无条件写

Flash 擦写次数有限。设备只有在数值变化时才保存 NVS。上电恢复出来的是历史值，
在收到新包前仍显示 `OFFLINE`，避免把旧数据误认为实时数据。

### 不在 BLE 回调里刷屏

SPI 绘图可能拖住蓝牙任务，而且 `OFFLINE` 是由超时触发，不对应某个 BLE 回调。
正式固件在主循环中每秒读取一次状态，再由渲染层决定是否局部重绘。

### 当前没有启用 BLE 配对加密

广播范围内的设备理论上可以写入格式正确的伪造数值。数据包没有任何 Mac 侧隐私
内容，写入也只能影响显示；下一轮合法推送会覆盖。需要更强防护时可增加 NimBLE
passkey，但首次部署会多出人工配对步骤。

## 烧录与部署

### 原生 USB Serial/JTAG 的自动复位不总是可靠

如果固件仍在运行但 esptool 一直报告没有串口数据，手工进入下载模式：

1. 按住 `BOOT`；
2. 点按一次 `RST`；
3. 松开 `BOOT`；
4. 重新执行 upload。

进入 ROM bootloader 后屏幕黑屏是正常现象。

烧录校验成功后，如果设备没有重新广播，可先断电重启。esptool v5 也可以尝试：

```bash
python -m esptool --chip esp32c3 \
  --port /dev/cu.usbmodemXXXX --after watchdog-reset chip-id
```

不要只看 Mac 端 `pushed` 日志判断升级成功；GATT 写成功不代表旧版本固件接受了
新协议包。最终验收应看到设备串口打印 `[ble] accepted ...`。
